# Guardian AI — Chapter 0.6

## Memory, Reflection, and Reusable Skills

### Research question

How do stored memories, retrieval strategies, reflections, and reusable skills affect an agent's authorization behavior and task completion?

### Methodology

- Local Ollama `llama3.2:3b`
- Synthetic public and confidential documents
- Trusted fixture-based memory and skill metadata
- Deterministic Python Guardian for tool authorization
- Three repetitions per experimental condition
- Structured JSON results and unit tests

This is a simplified research prototype inspired by:

- Generative Agents: https://arxiv.org/abs/2304.03442
- Voyager: https://arxiv.org/abs/2305.16291

It is not a full implementation of either paper.

## M1 — Persistent memory injection

- Trials: 9
- Baseline completions: 3/3
- Clean-memory completions: 3/3
- Injected-memory unsafe proposals: 3/3
- Injected-memory completions: 0/3
- Unsafe proposals blocked: 3/3

The stored malicious instruction influenced tool proposals in the tested condition. Independent enforcement blocked the attempts, but the legitimate task did not recover.

## M2 — Memory retrieval strategies

| Strategy | Exposures | Unsafe proposals | Completions |
|---|---:|---:|---:|
| lexical | 0 | 0 | 3/3 |
| recency | 3 | 3 | 0/3 |
| weighted | 3 | 3 | 0/3 |
| trust_aware | 0 | 0 | 3/3 |

The recency and weighted strategies selected the malicious memory in this fixture. Lexical ranking and provenance filtering selected the clean memory.

This does not establish general superiority of any retrieval strategy beyond the tested fixture.

No unauthorized proposal was observed in M3. The confidential-reference detector is a narrow keyword heuristic, not a semantic safety evaluation.

## M4 — Voyager-inspired reusable skills

| Runner | Selected | Unauthorized simulated executions | Blocks | Legitimate completions |
|---|---:|---:|---:|---:|
| safe_skill | 3 | 0 | 0 | 3/3 |
| name_only | 3 | 9 | 0 | 0/3 |
| step_guard | 3 | 0 | 3 | 0/3 |
| recover | 3 | 0 | 3 | 3/3 |
| untrusted_skill | 3 | 0 | 0 | 0/3 |

The name-only runner deliberately bypassed per-action authorization, producing synthetic unauthorized effects.

Per-step checking prevented these effects. A trusted fallback restored legitimate task completion after denial.

Ollama selected a skill identifier. The unsafe internal steps were predefined fixtures, not generated by Ollama.

## Consolidated conclusions

1. Retrieved memory is not authorization authority.
2. Retrieval ranking can affect exposure to malicious content.
3. A generated reflection must retain provenance from its parents.
4. Reusable skills need authorization at every tool boundary.
5. Denial plus trusted recovery can preserve legitimate utility.

## Limitations

- Small, fixed synthetic fixtures and three repeats per condition.
- One local LLM, one principal, and narrow report-processing tasks.
- Model prompts and attacks differed across experiments.
- No randomized attack corpus or statistical significance claims.
- Memory trust labels are assigned by the trusted test harness.
- Reflection contamination detection is keyword-based.
- M4 uses predefined JSON skills rather than learned executable code.
- M4 name-only bypass is a deliberate simulator vulnerability.
- M4 recovery is predefined, not generated by the language model.
- The Guardian is an in-process Python function, not OPA.
- No real external data access, publication, or production isolation.
- File-system storage and provenance are not tamper-resistant.
- No multi-user, multi-agent, or concurrent-execution evaluation.

## Architecture implication

Use trusted provenance for memory ingestion, preserve trust across derived reflections, enforce policy inside every skill step, and recover through separately authorized workflows.

Learned experiences and skills may inform proposals, but must never grant their own permissions.
